# 固定输入的单次推理分析

工作台先比较一个固定输入下的总体表现，再进入一条具有代表性的真实 trace。
推理栈 DAG 是 Kernel 分析入口；选择融合组、量化转换或算子后，查看对应的计算、
数据流、实际调用和硬件指标。完整 Kernel 与 CPU 列表在图下方折叠。

## 采样与总体指标

**要回答的问题**：这一配置的延时是否稳定，选中的 trace 能否代表该批次？

**最小方法**：固定输入内容、形状、预处理和噪声方式，预热 5 次、记录 10 次。
在本机保留全部样本顺序。总体数值取一个批次的中位数；CV 用样本标准差除以均值，
当前门槛为 5%。代表 trace 同时检查请求墙钟及主要热点的调用次数和累计时间。
第一批不稳定时最多补测一次，两批完整原始记录留本机，采用通过检查的一批。
仓库只保留一个真实代表 trace、样本数和必要的 CV/计数检查摘要；不把所有采样导入页面。
Profiler 启动可能引入瞬态；节点采集可先启用 profiler，再完成同样的 5 次预热。
只给后续 10 个测量窗口加分析标签，不事后剔除首个样本。

**输出解释**：总体中位数是批次统计。当前 trace 显示该次预测的真实时间线；
Kernel 详情默认选中该 trace 中最接近类内中位数的一次真实调用。
系统、DAG 和 Kernel 共用这一实例，不提供重复的采集选择框。跨层同构算子共享分析，按实际实现、形状、精度、
布局和启动配置区分类别。

**不能推断**：预热次数不等于稳定性证明；总延时稳定不等于每个 Kernel 稳定。
独立 Nsys 或 NCU 采集不是无 profiler 端到端批次中的同一次预测。

## 系统过程图

**要回答的问题**：当前栈的一次推理在哪执行各模块，输入、中间结果和复用对象怎样传递？

**最小方法**：核对已有实现描述，使用上下两条 CPU/GPU 通道；横向 `step` 只表示过程顺序。
现有记录通过 `python3 -m extractors.pi0_system_flow --output .local/staging/pi0-system-flow.json`
生成后审阅、promote，复用共享渲染器。新系统按有依据的模块与依赖扩展，不复制组件。

**输出解释**：
模块说明包括计算、读入、写出和有效复用范围；数据传递与 CPU 提交用不同连线。
后端计算图与 CUDA Graph 捕获边界分别标明。
初始化、设置 prompt 和稳态单次预测必须区分；不同栈的图像处理位置与中间结果去向按实际实现描述。

**不能推断**：图的宽度不是耗时；CPU 顺序提交不等于等待前一个 GPU 模块完成。
CPU/GPU 通道表示执行位置，张量传递箭头不说明物理总线或显存布局。不预画尚不存在的快慢双系统。

## Nsys：系统执行与 CPU 工作

**要回答的问题**：CPU 工作、提交、同步、拷贝和 GPU 执行怎样分布在请求窗口内？

**最小方法**：先查询本机 `nsys profile --help`，核对 CUDA Graph、CPU 调度、
函数采样和 OS runtime 支持。只采一个固定案例；需要逐 Kernel 时采用 node 模式，
graph 模式用于较低侵入的执行范围观察。调度与函数采样分别保留，原报告留本机。

**输出解释**：请求墙钟、CPU 多线程累计运行、GPU 已记录活动并集、API 调用墙钟
分别显示。函数采样只有时刻与样本权重；脱敏栈保留实际采样的层级。OS runtime
等待调用有调用时间，不能据此给整段时间贴上线程阻塞状态。设备同步记录独立于
主机 API 同步调用。离线 Perfetto 保留完整事件，概览按像素聚合后可点击放大。

**不能推断**：这些时间不能直接相加。没有记录的区间不能称为空闲；只有时间重叠
不能证明因果。Profiler 下的调用时间不能替代无 profiler 的请求延时。

## NCU：代表 Kernel 的计算与访存

**要回答的问题**：主要热点实际使用哪些执行资源，计算和数据搬运有什么特征？

**最小方法**：根据代表 trace 的耗时贡献与待解问题选择少量热点，复用已有匹配指标，
只补必要的代表 launch，不要求每个栈凑齐固定数量。
查询本机 `ncu --list-sections` 与 `ncu --query-metrics`，使用本机支持的计算、
存储、Launch 和 occupancy 指标。记录实际回放、缓存与时钟策略；核对实现、
形状、精度和 launch 配置后关联，保留独立采集身份。

**输出解释**：先看输入到输出的计算与数据流，再看 grid/block、寄存器、共享内存、
计算利用和缓存指标。Roofline 的工作量、流量和耗时必须属于同一对象与口径。
公式估算的 Kernel 边界流量明确标注“建模”，硬件计数器保留自身内存域。

**不能推断**：低 occupancy 或低 issue rate 单独不足以证明瓶颈。NCU 回放时间
不能加进请求延时；不能用 NCU 实测字节与 Nsys 时间拼成实测带宽。
未知 tile、warp 和流水线不套用其他 GPU 的教程结构。

NCU 关联还需区分签名/启动配置匹配与明确调用次序关联。同一 symbol 和 launch
资源可能覆盖不同矩阵维度；后者只有在固定输入的原始多次执行中核对完整顺序后才使用，
保存 `same_input_order_association` 与 `work_id_unavailable`，在折叠采集条件中列出关联方式与维度来源。
Nsys 的精确工作量与 Roofline 不因此换成 NCU 计时，也不为这类关联生成新的 NCU Roofline 点。

## 补充一个推理栈的记录

**要回答的问题**：新栈在什么实际输入与精度下有延时和 Kernel 证据，能否从比较页进入？

**最小方法**：先核对本机已有权重和原生支持范围，再用独立 5+10 批次生成结果。
`python3 -m extractors.fixed_case --help` 提供共享 E2E/节点导入入口；输入为本机结果、
审阅过的运行模板和精确符号规则。节点导入仅输出一个稳定代表，完整批次和符号映射留本机。
`python3 -m extractors.fixed_case_ncu --help` 核对原始输入标识、完整符号及 grid/block/寄存器/shared
配置后生成独立回放记录。所有候选经正常 staging/promote 校验，再构建并实际点击检查。

**输出解释**：本轮 Realtime-VLA 是已有 LIBERO 转换权重的 BF16、1 view/P48/C50/D10；
FlashRT 是原生 base 权重的 FP8/FP16、1 view/P48/C10/D10。后者固定动作块 10，
默认块 50 页面通过「查看已有测量」进入真实块 10 配置。融合组复用已有 DAG 与详情组件。

**不能推断**：相同 Pi0 名称不代表权重、精度或工作量相同，不能把 FlashRT 块 10 延时填进块 50。
有限输出检查不证明任务精度等价；签名与启动配置匹配不等于 NCU 直接记录了矩阵维度。

DAG 关联先核对精确 Kernel 类型、唯一实现调用点和代表 trace 的上下游事件顺序。
例如 `extractors.flashrt_gate_up_links` 在原有 trace 上补前缀 Gate/Up 投影关联，
保留后续 GEGLU 的独立耗时；完整符号、文件校验和逐层顺序审阅留本机。
由实现顺序确认的层范围不冒充 trace 中的显式层标签；定位 DAG 时保留所选调用与图视窗。

`extractors.flashrt_gate_up_roofline` 复用此代表 trace 生成一个 Kernel 配对：
主乘加按 2MNK，FP8 输入/权重读一次、FP16 输出写一次；alpha 与输出转换工作明确留在模型之外。
页面随所选真实调用更新吞吐和耗时，在表中显示实测吞吐 / 所选 Roofline 边界的参考百分比。
百分比的分母是同一算术强度处的理论点，曲线假设和建模范围放入折叠说明；canonical 已匹配效率仍按证据条件计算。

## 运行条件与复用

**要回答的问题**：时钟、功耗、温度与复用范围是否足以解释观察到的差异？

**最小方法**：记录设备型号、实际精度、功耗档位、时钟策略及可用遥测。
不自动修改功耗或锁频。复用对象分别记录计算结果、执行计划或存储，列出生产者、
消费者、值依赖和失效条件；准备、存储、读取成本未知就留空。

**输出解释**：生命周期图的等宽阶段表示有效范围，不表示实测时间。
观测内 Prefix K/V 复用、CUDA Graph 提交计划和当前实现的时间嵌入计算范围分别查看。
遥测注明与采集的时间对齐程度，未对齐记录只作为运行条件旁证。

**不能推断**：相同 prompt 不等于整段多模态 prefix 相同；Graph replay 不代表
跨观测缓存计算结果。局部 Roofline 差距不等于可实现的总加速比。

## 可视化审阅与参考

**要回答的问题**：是否能从总体表现进入同一实例的具体执行对象，并准确返回？

**最小方法**：按本轮改动选择相关页面，用实际浏览器检查桌面截图及对应的选择、返回和视窗。
布局变更时补查一个窄屏；修改 DAG 时用相同尺寸和选择做前后对照。
数据或离线资产变更时，记录首屏数据体积，并在断网的新浏览器环境首次打开本机 HTTP 页面与 Perfetto。

**输出解释**：界面应明确当前输入、批次统计、当前 trace 和所选调用；详细来源
放入折叠内容，首屏优先回答当前对象做什么、耗时多少、数据如何流动。

**不能推断**：截图不能验证交互和离线加载；空态不算真实图表验收。

本轮参考已核对的本地版本，不将参考实现的结构视为本次 Kernel 的执行事实：

- [XProf 的图选择](https://github.com/openxla/xprof/blob/5f7d9cf3309be97ff78b98abf05f279c602a98ac/frontend/app/components/graph_viewer/graph_viewer.ts)：图和详情共享选择。
- [HTA](https://github.com/facebookresearch/HolisticTraceAnalysis)：区间、关联和累计时间与跨度的区别。
- [PyProf](https://github.com/NVIDIA/PyProf)：由形状和精度元数据关联执行对象。
- [CUTLASS 的 GEMM 说明](https://github.com/NVIDIA/cutlass/blob/e6233cbac5d7c7a865c19c91cd684ceece19513c/media/docs/cpp/efficient_gemm.md)：矩阵计算与数据层次的表达。

## 数据留存与 agent 工作流

1. 写清当前输入实例和要回答的问题，先查看已有证据。
2. 仅为明确缺口采集；在本机检查稳定性并选择一个真实 trace。
3. 解析、脱敏、关联实现对象，保留必要指标和精简稳定性摘要。
4. 用已有公式生成当前理论场景，再渲染总体、DAG、热点与复用说明。
5. 用实际浏览器检查页面，区分观测事实、瓶颈假设和待验证条件。
6. 输出当前结论、证据限制与可复现的解析命令。问题已能回答时停止扩采。

原始报告、其他 trace、尝试性导出、截图和长审阅日志只放本机 `.local/`。
归档工具先备份再按引用关系精简 canonical；仓库不是历史采样库。
保留三个模型默认 BF16 的小型理论校验样本，其他精度由场景输入和公式按需生成。
固定版本查看器由准备脚本和哈希清单复现，不重复提交第三方发行二进制。
新增文件必须服务解析、验证或当前分析表达；优先减少重复数据，再考虑加载架构。
